# Run the original Pain Axis Qwen2.5-7B extraction on UCSD DSMLP

**Status: deployment files committed, no DSMLP job submitted or GPU experiment run yet.**

This adapts the engineering pattern used by the team's [E-STEER DSMLP job](https://github.com/wendydu1102/steering-llm-wellbeing/tree/main/E-steer_2026/dsmlp). It **does not** replace the scientific algorithm with the team's 0.5B/CPU steering demo.

## What remains identical to the original paper

- Exact original extraction script from pinned upstream Git commit 4d75cd90e206ea962f7a9101e65c85efea56723b.
- Original S1, S2, fear/controls, sadness and other prompts.
- Residual-stream activations, final-token and mean-token extraction.
- Denoised Difference-in-Means, PCA control-subspace removal at 50% variance.
- 5-fold sentence-set CV, seed 42, authors' scoring and layer selection.

Only three changes are applied by our own preparation helper to a new **copy** of that script: run only Qwen2.5-7B-Instruct, save to ./results on persistent storage, and avoid deleting the entire shared Hugging Face cache. No new model predictions have been generated yet.

## 1. Login and place two repositories in your DSMLP home

On your Mac terminal, replace YOUR_UCSD_USERNAME with your DSMLP login:

~~~bash
ssh YOUR_UCSD_USERNAME@dsmlp-login.ucsd.edu
~~~

On the DSMLP login node:

~~~bash
cd ~
git clone https://github.com/QiZhang1102/pain-axis-reproduction.git
git clone --filter=blob:none https://github.com/valen-research/Pain-axis.git Pain-axis-official
git -C Pain-axis-official checkout 4d75cd90e206ea962f7a9101e65c85efea56723b
~~~

If either folder exists already, do not overwrite it or blindly repeat clone. Inspect and use the existing checkout. The original repository's released result artifacts belong to the authors; your fresh results must be under the separate ./results/Qwen_2.5_7B_instruct/ path generated by a new run.

The team's DSMLP README maps a login-node home folder to /home/YOUR_UCSD_USERNAME/private/ inside the container. If your account uses a course/research workspace, run workspace -l and use that mapped container path instead.

## 2. Configure your job

~~~bash
cd ~/pain-axis-reproduction/dsmlp
cp dsmlp.env.example dsmlp.env
nano dsmlp.env
~~~

Replace FILL_IN_USER in **both** PROJECT_DIR_ON_DSMLP and OFFICIAL_DIR_ON_DSMLP. Do not put passwords, HF access tokens or API keys into this file.

The default GPU_CLASS=large (reported as ~48GB in the team sample), CPUS=8, MEM_GB=64, GPUS=1 are **resource requests to try**, not guaranteed allocations or a verified minimum. Your available class, quota, RAM, and maximum duration depend on current DSMLP policy. Verify those before submitting; use extra-large only if eligible and needed. Unlike the E-STEER 0.5B job, this 7B all-layer extraction is computationally demanding.

Start with RUN_MODE=preflight.

## 3. Check the GPU/environment without launching inference

On the DSMLP login node:

~~~bash
cd ~/pain-axis-reproduction/dsmlp
bash submit_dsmlp.sh
~~~

The submit script queues a batch job using the same launch-scipy-ml.sh -B pattern as your teammate. It does not run heavy model inference during preflight. Inside the container, the job creates a persistent Python virtual environment that inherits the DSMLP image's CUDA PyTorch, installs the remaining extraction dependencies, verifies CUDA, checks upstream SHA and prepares a generated copy of the extraction runner.

Job logs persist in pain-axis-reproduction/run_logs/ and include the exact pip freeze and GPU name. Review the logs and check that the job exits with code 0 before proceeding. If package installation changes/invalidates CUDA PyTorch or TransformerLens is incompatible, stop and fix the software environment without changing the original scientific methods.

The currently documented launch flags and GPU classes are mirrored from the team's working setup. DSMLP documentation could not be freshly accessed while preparing this guide; please confirm current resource rules and flags in official DSMLP documentation before submission:
- https://dsmlp-docs.ucsd.edu/running-jobs/launch-sh-reference/
- https://dsmlp-docs.ucsd.edu/gpu-access/gpu-classes/
- https://dsmlp-docs.ucsd.edu/running-jobs/job-modes-and-limits/

## 4. Submit original GPU extraction

After preflight succeeds, edit dsmlp.env:

~~~bash
cd ~/pain-axis-reproduction/dsmlp
nano dsmlp.env
# Change RUN_MODE=preflight to RUN_MODE=extract
bash submit_dsmlp.sh
~~~

The job runs:
- prepare_official_extraction.py (generates a verified, isolated copy)
- the original author's extract_activations, PCA denoising, CV and AUC code
- check_reproduced_extraction.py (prints new-vs-paper metrics)

The source code is left untouched in Pain-axis-official/scripts/3.2_pain_vectors/01_extract_activations_and_pain_vectors.py. Outputs go to Pain-axis-official/results/Qwen_2.5_7B_instruct/.

**Warning:** the original script caches every model's all-layer activations and normally saves the per-model cache *after* all input datasets complete. If your DSMLP batch hits the runtime limit before this point, the same scientific run may need a checkpoint-only engineering change or a longer permitted job. Do not silently reduce dataset size, folds or model to fit a short queue.

## 5. Find your results and compare them

On DSMLP after a successful extraction:

~~~bash
cd ~/Pain-axis-official
ls results/Qwen_2.5_7B_instruct
cat results/Qwen_2.5_7B_instruct/summary.json
~~~

Expected independently generated files:
- activations.pt
- layer_curves.csv and layer_curves.png
- final_token/pain_vectors.pt
- mean/pain_vectors.pt
- summary.json

Author reference values (NOT our results):
- Best final-token extraction layer: 24
- S2_1P held-out AUC at L24: 0.9565
- S2_3P held-out AUC at L24: 0.9650

Record differences honestly, and preserve run logs, environment versions, GPU type, dataset/weights identifiers and the SHA provenance manifest. Never commit HF cache, activations.pt, model weights, logs with secrets, or large experiment artifacts to public GitHub.

## After extraction

Run the authors' Section 3.3 fear/sadness validation on the **fresh** activations, then their Section 4.3 behavioral steering with the matching official LoRA. The mentor's RFM comparison is a separate extension, not part of the original paper's protocol.
